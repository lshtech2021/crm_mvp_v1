# CRM MVP — Data Model

PostgreSQL schema for a multi-tenant CRM. Types use native PostgreSQL enums where noted; `uuid` values are generated by the application or `gen_random_uuid()` as policy dictates.

---

## Shared types

| Type | Values / notes |
|------|----------------|
| `tenant_status` | `active`, `deactivated` |
| `user_role` | `admin`, `manager`, `rep`, `viewer` |
| `user_status` | `active`, `deactivated` |
| `deal_stage` | `qualification`, `proposal`, `negotiation`, `closed_won`, `closed_lost` |
| `task_priority` | `low`, `medium`, `high` |
| `task_status` | `to_do`, `in_progress`, `done` |

Enable `pg_trgm` for GIN trigram indexes used below.

| Name | Definition |
|------|------------|

**Indexes**

**Note:** `contacts` references `companies`; ensure migration order or deferrable FKs if circular creation is required.

## Relationships (ERD — text)

```
tenants
  ├──< users (tenant_id)
  ├──< contacts (tenant_id)
  ├──< companies (tenant_id)
  ├──< deals (tenant_id)
  ├──< tasks (tenant_id)
  ├──< dashboard_snapshots (tenant_id)
  └──  audit_logs.tenant_id (logical only, no FK)

users
  ├──< contacts.created_by
  ├──< companies.created_by
  ├──< deals (owner_id, created_by)
  └──< tasks (assignee_id, created_by)

companies
  ├──< contacts.company_id (optional)
  └──< deals.company_id

contacts
  └──< deals.primary_contact_id
  └──< tasks.contact_id (optional)

deals
  └──< tasks.deal_id (optional)
```

**Cardinality summary**

| From | To | Cardinality |
|------|-----|-------------|
| Tenant | Users, contacts, companies, deals, tasks, dashboard snapshot | 1 : N (snapshot enforced 1 : 1 at row level) |
| User | Contacts / companies (creator), deals (owner, creator), tasks (assignee, creator) | 1 : N |
| Company | Contacts | 1 : N (optional link) |
| Company | Deals | 1 : N |
| Contact | Deals (primary) | 1 : N |
| Deal | Tasks | 1 : N (optional) |
| Contact | Tasks | 1 : N (optional) |

## Migrations

Schema changes are managed with **Alembic** (revision chain, upgrade/downgrade, autogenerate where appropriate with manual review).

**Initial migration scope**

- Create PostgreSQL enum types: `tenant_status`, `user_role`, `user_status`, `deal_stage`, `task_priority`, `task_status`.
- Enable extension `pg_trgm` (and any helper extension required for chosen trigram index definitions).
- Create tables in dependency order: `tenants` → `users` → `companies` → `contacts` (with `company_id` FK) → `deals` → `tasks` → `audit_logs` → `dashboard_snapshots`.
- Add all primary keys, unique constraints, partial unique index on `contacts (tenant_id, email)`, partial index on `tasks`, and remaining secondary indexes including trigram indexes.
- Optional: triggers or application layer for `updated_at` maintenance; document in application spec if not in first migration.

## Tenant scoping

All tenant-owned business data lives in tables that include `tenant_id` (`users`, `contacts`, `companies`, `deals`, `tasks`, `dashboard_snapshots`). `audit_logs` stores `tenant_id` for partitioning queries but has no FK.

The application **auto-filters every query** by the current tenant’s `tenant_id` using **SQLAlchemy event listeners** (for example, `before_compile` or ORM load/query events) so that SELECT, UPDATE, and DELETE operations cannot accidentally span tenants. Inserts must set `tenant_id` from the authenticated context, not from untrusted client input. Cross-tenant identifiers in URLs or APIs are rejected or ignored in favor of the session tenant.

Global uniqueness on `users.email` is a product choice; listing and mutating users still go through tenant-scoped query filters so reps only see users in their tenant while the database enforces email uniqueness across the system.
